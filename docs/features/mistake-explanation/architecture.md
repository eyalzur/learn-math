# הסבר דרך פתרון אחרי טעות — Architecture

## Overview
מודול חדש וטהור (`src/data/explain.ts`) שמקבל `Problem` ומחזיר רשימת שלבים מובנית,
ורינדור של הרשימה הזו ב-`Practice.tsx` מתחת למשוב הקיים. אין state חדש ואין תלות חדשה.

## Affected Files / Components
- **`src/data/explain.ts`** (חדש) — הלוגיקה שממירה תרגיל לשלבי הסבר. נמצא ליד
  `exerciseSets.ts` כי זו לוגיקה על התרגילים עצמם, לא על ה-UI.
- **`src/components/Practice.tsx`** (עדכון) — קורא ל-`explainProblem` ומרנדר את הבלוק
  כשה-feedback הוא `"wrong"`.
- **`src/App.css`** (עדכון) — סגנון לבלוק ההסבר ולעטיפת הביטויים החשבוניים ב-LTR.

## Data / State Changes
אין state חדש. `Practice.tsx` כבר יודע מתי התשובה שגויה (`feedback === "wrong"`) ואיזה
תרגיל מוצג (`problem`) — שני אלה מספיקים, וההסבר נגזר מהם בזמן הרינדור.

טיפוס חדש שמיוצא מ-`explain.ts`:

```ts
interface ExplanationStep {
  label: string;  // הטקסט העברי, למשל "קודם העשרות:"
  math: string;   // הביטוי החשבוני, למשל "67 + 10 = 77"
}
```

ההפרדה בין `label` ל-`math` היא לא קוסמטית — היא הדרך שבה design.md דורש למנוע את באג
הכיווניות: כל חלק מרונדר באלמנט משלו עם כיוון משלו, במקום להסתמך על אלגוריתם ה-bidi
של הדפדפן על מחרוזת מעורבת.

חלק מהשלבים (המקרים הטריוויאליים של 0) הם טקסט בלבד בלי ביטוי חשבוני — במקרה כזה
`math` יהיה מחרוזת ריקה והרינדור מדלג עליו.

## Technical Approach
`explainProblem(problem: Problem): ExplanationStep[]` עושה switch על `problem.op`
ומפצל לארבע פונקציות פנימיות, אחת לכל פעולה, שכל אחת מיישמת את כללי design.md:

- **חיבור** — 0 → משפט יחיד; שני חד-ספרתיים → ספירה קדימה מהגדול (רשימת המספרים
  נבנית בלולאה); אחרת פיצול `b` ל-`Math.floor(b/10)*10` ו-`b%10`, ודילוג על שלב שערכו 0.
- **חיסור** — 0 → משפט יחיד; `b >= 10` → פיצול לעשרות ויחידות; `a > 10 && b > a%10`
  → עצירה בעשרת (`a - a%10`) ואז השארית; אחרת ספירה אחורה.
- **כפל** — גורם 10 → כלל האפס; `s <= 4` → חיבור חוזר של `l` (מחרוזת מצטרפת ב-`+`);
  `s === 5` → חצי מ-`10*l`; `s >= 6` → `5*l + (s-5)*l` בשני שלבים.
  `s`/`l` הם המינימום והמקסימום של הגורמים, כדי שהחיבור החוזר תמיד יהיה הקצר משניהם.
- **חילוק** — שני שלבים קבועים דרך לוח הכפל (`b × ? = a`, ואז `b × q = a`).

כל ענף מסתיים בערך מוחזר, ולכל פעולה יש ענף ברירת מחדל, כך שכל צירוף מספרים מקבל
לפחות שלב אחד. הפונקציה טהורה — אין בה תלות ב-React או ב-DOM — ולכן אפשר לבדוק
אותה ישירות מול כל התרגילים הקיימים.

ב-`Practice.tsx` הרינדור מותנה:

```tsx
{feedback === "wrong" && (
  <div className="explanation"> ... </div>
)}
```

ב-CSS, מחלקה `.explanation-math` מקבלת `direction: ltr` ו-`unicode-bidi: embed`,
בדיוק כמו הפתרון שכבר עובד ב-`.problem-box`.

## Edge Cases
- **0 באחד האגפים** (`0 + 9`, `20 − 0`) — מטופל במפורש בענף ראשון בכל פעולה, אחרת
  ספירה של 0 צעדים הייתה מייצרת רשימה ריקה.
- **חיסור בלי מעבר עשרת** (למשל 18 − 3) — לא מופיע בסטים הקיימים, אבל הענף קיים
  (ספירה אחורה) כדי שהוספת תרגילים עתידית לא תיפול.
- **חיבור שבו ליחידות אין תרומה** (`40 + 40`) — שלב היחידות מושמט במקום להציג
  `80 + 0 = 80`.
- **`10 × 10`** — נופל בענף כלל האפס לפני ענף `s >= 6`, ולכן לא מייצר פיצול מיותר.
- **תוצאות חילוק שלמות בלבד** — כל סט `div-simple` וה-`mixed` מתחלקים ללא שארית,
  ו-`answerOf` כבר מניח את זה. ההסבר מניח אותו הדבר; חילוק עם שארית יצריך שינוי
  מוצרי, לא רק טכני.
- **כיווניות** — הסיכון האמיתי היחיד כאן; מנוטרל על ידי הפרדת `label`/`math`.

## Risks / Tradeoffs
- הלוגיקה גדלה עם מספר סוגי התרגילים. כל עוד יש ארבע פעולות זה קובץ קריא; אם יתווספו
  שברים או אחוזים, כדאי יהיה לשקול העברת ההסבר לנתוני התרגיל עצמו במקום חישוב גנרי.
- נבחר **לחשב** את ההסבר ולא לאחסן אותו ב-`exerciseSets.ts` לצד כל תרגיל: אחסון היה
  מכפיל את הנתונים, ומחייב לזכור לכתוב הסבר לכל תרגיל חדש — בדיוק סוג הדבר שנשכח
  ומייצר תרגיל בלי הסבר, מה שסותר קריטריון קבלה מפורש.
- ההסבר לא מתייחס לתשובה שהתלמיד/ה הזינו (זה מחוץ ל-scope), ולכן אין כאן ניתוח שגיאות.
