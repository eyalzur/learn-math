# פריסה אוטומטית של השרת — Design

## Overview
אין כאן ממשק אפליקציה — מה שצריך עיצוב הוא מה **המשתמש** (לא מתכנת) רואה בדף
ה-Actions של GitHub כשפריסה קורית, נכשלת, או לא קורית; ומסמך הגדרה חד-פעמי
שהוא יכול לבצע בלי לנחש. שלושת אלה הם המסך של הפיצ'ר הזה.

## Screens / States

המשתמש רואה את הפיצ'ר הזה בשלושה מקומות בלבד.

### 1. רשימת הריצות ב-Actions

```
Actions
├─ Deploy server to Cloud Run     ← חדש
├─ Deploy to GitHub Pages
├─ Tests
└─ Version bump check
```

**השם:** `Deploy server to Cloud Run`. נבחר כך שיהיה מובן למי שלא כתב אותו וקריא
לצד השכנים שלו: הפועל הראשון זהה ל-`Deploy to GitHub Pages` (אותה משפחה — "משהו
מתפרסם"), והמילים `server` ו-`Cloud Run` מבדילות אותו ממנה בלי להצריך ידע. השם
הנדחה: `Cloud Run` לבד או `server-deploy` — הראשון לא אומר מה קורה, השני נראה
כמו שם קובץ.

### 2. תוצאת ריצה בודדת — שלושה מצבים, לא שניים

זו ההכרעה המרכזית בעיצוב הזה. המצב השלישי הוא התשובה לסיכון שה-product-spec
מזהיר ממנו: *"אין שום סימן לכך"*.

| מה קרה | מה המשתמש רואה | למה |
|---|---|---|
| נדחף קוד שנוגע ב-`server/` | ✅ ריצה ירוקה, מסתיימת ב-`deployed: <URL>` | הפריסה קרתה |
| נדחף קוד שלא נוגע ב-`server/` | ✅ ריצה ירוקה וקצרה, `no changes under server/ — nothing to deploy` | **הפריסה לא קרתה, וזה תקין** |
| משהו נשבר | ❌ ריצה אדומה, עם שורת הכוונה (למטה) | צריך טיפול |

**דרישת העיצוב:** כל push ל-`main` חייב להשאיר תוצאה גלויה ומוסברת-בעצמה — גם
כשלא נפרס כלום. הסיבה: אם "לא נפרס" ו"נשבר לפני שהתחיל" נראים אותו דבר (כלומר:
כלום), המשתמש לא יכול להבדיל ביניהם, ובדיוק ההנחה השגויה הזו ("בטח התעדכן") היא
מה שהפיצ'ר בא למנוע. **היעדר ריצה הופך בעצמו לסימן שמשהו לא בסדר** — וזו מסקנה
שאפשר להסיק רק אם בדרך כלל *יש* ריצה.

זה **אינו** סותר את קריטריון הקבלה "push שלא נוגע ב-`server/` אינו מפעיל פריסה" —
הוא אכן לא מפעיל **פריסה**; הוא רק מדווח בקול שלא הייתה כזו. עלות: ריצה של כמה
שניות בכל push. תמורה: אין מצב שקט ודו-משמעי.

המנגנון (filter של `paths` מול בדיקה פנימית) הוא הכרעה של tech-lead — העיצוב
קובע רק את מה שנראה.

### 3. כשל — הפלט מכוון לפעולה, לא ל-stack trace

התקדים בריפו הוא `scripts/check-version-bump.mjs`, שכשהוא נכשל מסיים ב-
`run: npm run bump:feature` — כלומר **אומר מה לעשות**, לא רק מה שגוי. אותו דפוס
כאן: כשהפריסה נכשלת, השורות האחרונות בלוג (אחרי הפלט של `gcloud`, לא במקומו) הן
בלוק הכוונה קבוע:

```
deploy failed. the usual causes, in order of likelihood:
  1. the GitHub->Google Cloud permission expired or was removed
  2. the billing account got unlinked from the project
  3. the server code itself does not build
see: server/README.md, section "פריסה אוטומטית — הגדרה חד-פעמית"
```

שלוש הסיבות אינן ניחוש: **שתיים מהן קרו בפועל בהקמה הידנית** ב-2026-08-29 (חשבון
חיוב שהיה קיים אך לא מקושר; הרשאה חסרה לחשבון השירות), ומתועדות ב-
`server/README.md`. הן מסודרות לפי סבירות, כי משתמש שאינו מתכנת יתחיל מלמעלה.

**שפת הפלט — אנגלית, במכוון.** הפרויקט מתקשר עם המשתמש בעברית, אבל הפלט הזה יושב
בתוך ממשק אנגלי של GitHub, מיד אחרי פלט אנגלי של `gcloud`, ולצד
`check-version-bump.mjs` שכבר כותב אנגלית. עברית בתוך הרצף הזה תיראה כמו תקלת
קידוד, לא כמו עזרה. **המסמך שאליו הפלט מפנה — כן בעברית**, כי שם הוא באמת קורא
ופועל.

## Copy

אין מחרוזות באפליקציה. הטקסטים היחידים שנוספים:

**בממשק GitHub (אנגלית, כמוסבר למעלה):**
- שם ה-workflow: `Deploy server to Cloud Run`
- הצלחה: `deployed: <service URL>`
- אין מה לפרוס: `no changes under server/ — nothing to deploy`
- כשל: בלוק שלוש הסיבות שלמעלה, מסתיים ב-
  `see: server/README.md, section "פריסה אוטומטית — הגדרה חד-פעמית"`

**במסמך ההוראות (עברית):**
- כותרת הסעיף החדש: `פריסה אוטומטית — הגדרה חד-פעמית`
- פתיח שמסביר את המצב לפני שמתחילים: `עד שתסיימו את הצעדים כאן, הפריסה האוטומטית
  לא תעבוד וריצות הפריסה ב-GitHub ייכשלו. זה צפוי — זו לא תקלה.`
  (קריטריון קבלה מפורש ב-product-spec: ריצה אדומה ראשונה לא צריכה להיראות כמו
  שבר.)

## Interaction Flow

### הזרימה הרגילה — אחרי ההגדרה
1. המשתמש ממזג PR שנוגע ב-`server/`.
2. בלי שיעשה דבר, ריצה בשם `Deploy server to Cloud Run` מופיעה ב-Actions.
3. היא מסתיימת ירוקה, והשורה האחרונה בה היא הכתובת שנפרסה.
4. אם הוא לא בדק — אין צורך. אם הוא כן בדק — התשובה שם, במקום שהוא כבר מכיר.

### הזרימה כשלא נפרס
1. המשתמש ממזג PR שנוגע רק בלקוח.
2. ריצה מופיעה, נגמרת תוך שניות, ירוקה, ואומרת שלא היה מה לפרוס.
3. **הוא לא צריך לתהות** אם השרת התעדכן: כתוב שלא, וכתוב למה.

### הזרימה בכשל
1. ריצה אדומה מופיעה ב-Actions (וגם במייל, לפי הגדרות ההתראות הרגילות של GitHub).
2. הוא פותח אותה. בתחתית הלוג — שלוש הסיבות והפניה למסמך.
3. הוא הולך למסמך, מוצא את הסעיף בעברית, ומבצע.
4. **האתר בינתיים התפרסם כרגיל** — הכשל הזה לא נגע בו (קריטריון קבלה).

### ההגדרה החד-פעמית
מתרחשת פעם אחת, לפני הכל, ומתוארת במסמך.

## מבנה מסמך ההגדרה

**איפה הוא חי:** סעיף חדש ב-`server/README.md`, לא מסמך נפרד. שם כבר יושבות
הפריסה הידנית ושני המכשולים שהתגלו — פיצול לשני מסמכים יוצר בדיוק את הסיכון
שהמשתמש יקרא את הלא-נכון. סדר הסעיפים בקובץ: הפריסה הנוכחית → הגדרה חד-פעמית
(חדש) → פריסה ידנית (נשארת, כפי שה-product-spec דורש).

**איך הוא כתוב** — שלושה כללים, שכולם נובעים מטעויות אמיתיות שקרו היום:

1. **ערכים אמיתיים, לא placeholders.** ההוראה תכיל `learn-math-506923`, לא
   `<PROJECT_ID>`. היום נכשלה פקודה כי הופיע בה `learn-math` (שם התצוגה) במקום
   מזהה הפרויקט האמיתי. placeholder הוא הזמנה לנחש.
2. **לכל צעד — מה אמור לחזור.** לא רק "הרץ X", אלא גם "אמור להחזיר Y". זה מה
   שמאפשר למי שאינו מתכנת לדעת שהוא בכיוון הנכון במקום לגלות שלוש פקודות אחר כך.
3. **מה שהמשתמש מדביק ל-GitHub — במפורש איפה ואיך.** שם ההגדרה, המסך המדויק
   (Settings → ...), ומה בדיוק להעתיק. זה החלק היחיד שיוצא מהטרמינל ועובר לממשק
   אחר, ולכן הכי קל לטעות בו.

## Accessibility / RTL notes

**אין כאן מסך של האפליקציה**, ולכן הבאג החוזר של הפרויקט (ביטוי חשבוני שמתהפך
בתוך משפט עברי) אינו רלוונטי — אין ביטויים חשבוניים, אין מספרים שהתלמיד/ה קורא/ת,
ואין רינדור שאנחנו שולטים בו.

מה שכן נבדק, כי יש כאן טקסט שהמשתמש קורא:

- **פלט ה-CI** — אנגלית בלבד, ולכן אין ערבוב כיווניות כלל. זו אחת הסיבות
  להכרעה הזו: לוג GitHub הוא סביבה LTR שאיננו שולטים בה, ומחרוזת עברית בתוך
  שורה עם כתובת URL ומזהי פרויקט הייתה בדיוק המקרה שהפרויקט כבר נכווה בו
  שלוש פעמים — רק בלי שום דרך לתקן, כי אין לנו CSS על הלוג של GitHub.
- **מסמך ההגדרה** — עברית ב-Markdown. מזהי פרויקט, פקודות וכתובות יושבים
  ב-code blocks, שמוצגים LTR מובנה בכל מציג Markdown (GitHub כולל). זה מונע
  את ההיפוך בלי שנצטרך לסמוך על אלגוריתם ה-bidi על טקסט מעורב — אותו עיקרון
  שמנחה את `.problem-box` באפליקציה: **טקסט עברי וערך טכני הם שני אלמנטים
  נפרדים, לא מחרוזת אחת.**
- **שם ה-workflow** — אנגלית, כמו שלושת הקיימים. אין ערבוב.

## Acceptance Criteria Check

- **פריסה מופעלת כשקוד השרת מגיע ל-`main`**: yes — מצב 1 בטבלה.
- **push שלא נוגע ב-`server/` אינו מפעיל פריסה**: yes — מצב 2. הפריסה אינה
  מתרחשת; מה שכן מתרחש הוא דיווח קצר שלא הייתה פריסה, וזה מה שמונע את הדו-משמעות.
- **אפשר להפעיל פריסה ידנית מדף ה-Actions**: yes — הכפתור הסטנדרטי של
  `workflow_dispatch`, אותה חוויה בדיוק כמו ב-`Deploy to GitHub Pages` שהמשתמש
  כבר מכיר. אין צורך בעיצוב חדש.
- **כשלון אינו מונע מהאתר להתפרסם / אינו משנה `tests` ו-`version-check`**: yes —
  workflow נפרד לגמרי, שם נפרד, ריצה נפרדת. הזרימה בכשל מציינת זאת במפורש.
- **הפריסה הקיימת של האתר לא משתנה**: yes — לא נגענו ב-`deploy.yml` בעיצוב הזה.
- **כשלון גלוי**: yes — ריצה אדומה, ובנוסף בלוק ההכוונה שהופך אותה לפעילה.
- **תיעוד ההגדרה החד-פעמית, כרשימת צעדים מדויקת**: yes — מבנה המסמך למעלה,
  כולל שלושת כללי הכתיבה.
- **כתוב במפורש שעד ההגדרה זה לא יעבוד**: yes — משפט הפתיח של הסעיף, מצוטט
  ב-Copy.
- **תיעוד הפריסה הידנית נשאר**: yes — נשאר כסעיף נפרד באותו קובץ.
- **שום סוד לא נכנס לריפו**: yes מבחינת העיצוב — המסמך מתאר *לאן* המשתמש מזין
  ערכים בממשק של GitHub, ולא מכיל אותם. (האכיפה הטכנית היא של tech-lead.)

## רוויזיה — 2026-08-31: אין שינוי עיצובי

התיקון (product-spec.md, "רוויזיה — 2026-08-31") הוא פין מפורש של חשבון
השירות בפקודת ה-`gcloud` — אין מסך, אין טקסט חדש, אין שינוי בזרימת ה-Actions
שכבר תוארה למעלה. הריצה עדיין ירוקה/אדומה באותו מקום, באותה צורה.

**התאמה חשובה למה שכבר כתוב למעלה, לא סתירה אליו:** "כשלון גלוי — הוא מופיע
כריצה אדומה" (Acceptance Criteria Check, "כשלון גלוי") התייחס לכשלון **בפריסה
עצמה**. מה שקרה בפועל הוא סוג אחר: הפריסה **הצליחה** (ריצה ירוקה) בזמן שהיא
שינתה בשקט זהות קריטית. זה לא כשל בעיצוב הזה — ה"מסך" (ריצת Actions) מעולם
לא הבטיח לדווח על תוכן הפריסה, רק על הצלחתה הטכנית. אין כאן פער לתקן בעיצוב;
הפער היה בהנחה השגויה בארכיטקטורה (ראו tech-lead) שהפקודה משמרת את חשבון
השירות מעצמה.
