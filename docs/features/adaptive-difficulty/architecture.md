# קושי מסתגל — תרגילים מטמפלייט — Architecture

## Overview
נושא `חיבור עד 100` מקבל שדה חדש ואופציונלי, `adaptive`, על ה-`Topic` שלו. כשהוא קיים,
הניווט מדלג ישר לתרגול עם `Question[]` שנבנה ב-runtime מטמפלייטים קיימים (לא כתוב
מראש), ורמת קושי (`1`–`5`) שמתעדכנת אחרי כל תשובה. `Practice.tsx` עצמו כמעט לא משתנה —
מקבל `callback` אופציונלי חדש אחד שקורה לו אחרי כל תשובה, ומזין את השאלה הבאה מבחוץ.

## Data / State Changes

### `Topic.adaptive` — שדה אופציוני חדש ב-`curriculum.ts`
```ts
export interface AdaptiveConfig {
  /** בונה שאלה אחת בקושי נתון. rng אופציונלי לבדיקות דטרמיניסטיות (qa). */
  generate: (difficulty: number, rng?: () => number) => Question;
  minDifficulty: number;
  maxDifficulty: number;
  initialDifficulty: number;
  /** קושי אחרי תשובה — סטרייק נכונות/טעויות רצופות, לא רק "נכון/לא נכון" בודד. */
  nextDifficulty: (current: number, wasCorrect: boolean, streak: number) => number;
  questionCount: number; // 10, כמו כל תרגול אחר היום
}

export interface Topic {
  // ...קיים, ללא שינוי...
  adaptive?: AdaptiveConfig;
}
```
תוסף בלבד — כל טופיק אחר (`22`+ נושאים) לא מגדיר `adaptive`, אז `topic.adaptive` הוא
`undefined` אצלו, וכל נתיב קוד שכבר קיים ממשיך בדיוק כמו שהוא בלי לבדוק את השדה החדש
בכלל.

### מצב חדש ב-`App.tsx`
```ts
const [adaptiveSession, setAdaptiveSession] = useState<{
  difficulty: number;
  streak: number; // חיובי = רצף נכונות, שלילי = רצף טעויות
  questions: Question[];
} | null>(null);
```
נוצר כשנכנסים לתרגול של נושא אדפטיבי (`questionCount` שאלות, כולן נוצרות מיד ב-
`initialDifficulty` — לא רק הראשונה, כדי ש-`lesson.questions.length` יהיה `10` מהרגע
הראשון ו-`isLast`/"שאלה X מתוך 10" ב-`Practice.tsx` יעבדו בלי שום שינוי שם). מתאפס
ל-`null` ביציאה מהתרגול (`onExit`/`onFinish`), כך שכניסה חדשה מתחילה קושי טרי — תואם
להחלטת המוצר ש"קושי לאורך זמן" מחוץ להיקף.

### שאלה שלישית שלא הופנתה אליי במפורש, אבל צריכה הכרעה: זהות ה-`lesson` בזיכרון
`screen.practice.lesson.questions` (הקיים) ו-`adaptiveSession.questions` (החדש) הם
**אותו מידע פעמיים** אם לא נזהרים. הפתרון: כש-`topic.adaptive` קיים, `lesson` שנבנה
עבור `<Practice>` מחושב מ-`adaptiveSession.questions` בכל רינדור (לא נשמר בתוך
`screen` בנפרד) — כלומר `screen.name === "practice"` עדיין נושא `topic`, אבל `lesson`
לתרגול אדפטיבי נגזר, לא מאוחסן. `finish()`/`onExit` משתמשים ב-`topic` בלבד לחישוב
מסך היעד, בדיוק כמו היום.

## Technical Approach

### הטמפלייטים (`adaptiveAdd100.ts`)
חמישה דפוסים, ממופים ישירות מ-`docs/features/mika-grade2-content/tests.md` (הדפוסים
שכבר זוהו תכנותית בעבודת הריוויו של השבוע — לא דפוסים חדשים):
1. מספר חד-ספרתי מתווסף לדו-ספרתי, בלי מעבר עשרה (יחידות `+` יחידות `< 10`).
2. אותו דפוס, כש-`1` יחידה בדיוק (וריאציית ניסוח "יחידה" יחיד, לא "יחידות" רבים —
   **חובה** להבדיל, זו בדיוק ההקפדה שהתגלתה בכתיבה הידנית של אותם רמזים).
3. שני מספרים שהם עשרות שלמות (`30 + 40`).
4. שני מספרים דו-ספרתיים, בלי מעבר עשרה.
5. מעבר עשרה (יחידות `+` יחידות `≥ 10`) — כולל את שלב "עוברים עשר, מעבירים עשרת אחת".

כל דפוס הוא זוג פונקציות: `pickOperands(rng)` (מגריל `a`,`b` תואמים למגבלות הדפוס —
למשל דפוס `1`: `a` דו-ספרתי אקראי, `b` חד-ספרתי אקראי כך שסכום היחידות `< 10`) ו-
`build(a, b, rng)` שמרכיב `Question` שלם: `prompt`, `hints` (שני המחרוזות שכבר קיימות
ב-`grade2.ts`, עם `a`/`b`/`tens`/`units` מוצבים ב-`template literal` במקום כתובים
פעם אחת), `steps` (אותה לוגיקת בנייה שכבר נכתבה לתיקון של השבוע — יחידות עם יחידות,
עשרות עם עשרות, כולל "מעבירים עשרת אחת" בדפוס `5`), ו-`analogy` שנבחר אקראית מתוך
**מאגר** של הדימויים הקיימים לאותו דפוס (`"מדבקות"`, `"גולות"`, `"בלונים"`, `"ספרים"`,
`"קלפי משחק"`...) עם המספרים המוצבים — לא דימוי חדש שלא נבדק.

`generate(difficulty, rng = Math.random)`: ממפה קושי `1`–`5` לתת-קבוצת דפוסים
כשירים (קושי `1` → דפוסים `1`+`3`; קושי `3` → דפוס `4`; קושי `5` → דפוס `5` בלבד וכו',
פירוט מדויק נשאר לפיתוח, לא מוכתב כאן), בוחר דפוס אקראי מתוכה, ואז מגריל/בונה שאלה.
`rng` מוזרק כדי ש-QA יוכל להריץ אלף אינסטנסים דטרמיניסטית בבדיקה (ראו QA notes ב-Edge
Cases).

### לוגיקת הקושי
- מתחיל בקושי `1` (התחלה בטוחה) — תואם לכלל התוכן הקיים "שיעור מטפס מקל לקשה", לא
  מתחיל באמצע.
- **שתי תשובות נכונות ברצף** מעלות קושי ב-`1` (מקסימום `5`) — לא תשובה בודדת, כדי
  שניחוש מזל אחד לא יזרוק קדימה מהר מדי.
- **תשובה שגויה אחת** מורידה קושי ב-`1` (מינימום `1`) ומאפסת את הרצף — תגובה מיידית
  לקושי אמיתי, לא ממתינה לדפוס.
- המספרים (`2` נכונות לעלייה, `1` טעות לירידה) הם הכרעת tech-lead, לא product — נקודה
  פתוחה לכיוונון אחרי שימוש אמיתי, לא קבועה בסלע.

### זרימת השאלה הבאה
כל `10` השאלות **נוצרות מראש**, בקושי ההתחלתי, ברגע הכניסה לתרגול. אחרי כל תשובה
(`onAnswered`), אם יש עוד שאלה קדימה במערך (`index + 1 < questionCount`), היא
**מוחלפת** (לא רק הראשונה — כל שאלה עתידית שעדיין לא הוצגה) בשאלה חדשה שנוצרת ברמת
הקושי המעודכנת. שאלות שכבר הוצגו/נענו אינן משתנות. זה נמנע מבעיית תזמון: אם המערך
היה גדל שאלה-שאלה (מתחיל באורך `1`), `isLast` ב-`Practice.tsx` היה מחושב נכון רק
ברינדור הבא, ולא ברגע ש-`checkAnswer` עצמו רץ (הוא צריך את `isLast` הנוכחי כדי להחליט
אם להתחיל את הספירה לאחור) — אורך קבוע של `10` מההתחלה עוקף את זה לגמרי.

## Edge Cases
- **דקדוק יחיד/רבים ("`1` יחידה" מול "`X` יחידות")** — הגנרטור **חייב** לבחור את
  התבנית הנכונה לפי הערך שהוא עצמו הגריל, לא רק להעתיק את שתי הגרסאות הקיימות בלי
  תנאי. זו בדיוק סוג הטעות שנתפסה בעבודה הידנית של השבוע.
- **כפילות שאלות בתוך סשן** — לא נדרש למנוע לגמרי (המספרים סופיים והדגימה אקראית),
  אבל `generate` עדיף שינסה שוב פעם אחת אם יצא בדיוק אותו `(a, b)` כמו שאלה קודמת
  באותו סשן, כדי ש-`10` שאלות לא יתחילו בשתיים זהות ברצף במקרה.
- **`verticalSum`/`methodSentence` כבר עובדים על כל שאלה שמתאימה לצורה שלהם**, בלי
  שינוי — הם פונקציות גנריות על `prompt`+`answer`, לא רשימה קבועה של שאלות. שאלה
  שנוצרה ב-runtime מקבלת מאונך ומשפט שיטה בדיוק כמו שאלה כתובה, בחינם.
- **`content.spec.ts` לא רואה שאלות שנוצרו ב-runtime בכלל** — הכללים שם (רמז לא נותן
  את התשובה, חשבון של `steps` נכון, וכו׳) רצים על `grades` הסטטי בלבד. זו לא "בעיה
  שנשארה פתוחה" בשקט — זה בדיוק למה QA צריך בדיקה מסוג אחר (ראו Risks/Tradeoffs).

## Risks / Tradeoffs
- **`30` השאלות הכתובות של `add100` נשארות בקוד, לא בשימוש בניווט.** במכוון: זה
  פיילוט (החלטת product), ואם הוא לא מוכיח את עצמו, החזרה למצב הקודם היא מחיקת שדה
  `adaptive` אחד — לא שחזור `30` שאלות שנמחקו. העלות: קוד "מת" זמנית בקובץ אחד.
- **בדיקות תוכן קיימות (`content.spec.ts`) לא מכסות שאלות שנוצרו ב-runtime.** זה
  דורש שכבת בדיקה **חדשה** ב-QA: הרצת `generate()` מאות פעמים על פני טווח הקושי
  המלא, והרצת **אותם כללים** (רמז לא חושף תשובה, `steps` מחשבים נכון, וכו׳) על
  הפלט — לא ריוויו אנושי של כל אינסטנס אפשרי (זה כבר הוגדר Out of Scope ב-product-
  spec), אלא בדיקה תכנותית שמחליפה אותו לתוכן שנוצר, לא לתוכן כתוב.
- **קושי מתחיל מ-`1` בכל סשן, לא נזכר בין ביקורים.** מוכר ומכוון (Out of Scope
  ב-product-spec) — אם מיקה שולטת בנושא, כל סשן חדש שוב מתחיל בקל. זה בדיוק מה
  ש"אבחון קשיים לאורך זמן" (פיצ'ר נפרד, לא מתוכנן עדיין) אמור לפתור בעתיד.

## Implementation Notes

נבנה בדיוק לפי המסמך הזה — חמישה דפוסים ב-`adaptiveAdd100.ts`, `Topic.adaptive` תוסף
ב-`curriculum.ts`, `onAnswered` יחיד ב-`Practice.tsx`, מערך `10` שאלות שנוצר מראש
ב-`App.tsx` ומוחלף רק בתאים שלא הוצגו עדיין. `30` השאלות הכתובות של `add100` נשארו
ב-`levels` בלי נגיעה, בדיוק כמתוכנן.

מיפוי הקושי שנקבע בפועל (לא הוכתב במסמך זה, הכרעת פיתוח):
1. עשרות שלמות (הכי פשוט לעין — מספרים "עגולים")
2. מספר חד-ספרתי מתווסף לדו-ספרתי, בלי מעבר עשרה
3. שני דו-ספרתיים, בלי מעבר עשרה
4. מעבר עשרה, עשרות מוגבלות (`≤5`)
5. מעבר עשרה, טווח מלא

שני באגים אמיתיים נתפסו ותוקנו ע"י בדיקה מבוססת-property (סקריפט חד-פעמי, RNG עם
זרע קבוע, `2500` אינסטנסים על פני כל טווח הקושי, חישוב עצמאי מחדש של כל `step`):

- **`carriedTens` חישב ספרת-עשרות במקום ערך-עשרות** — `tensA + tensB + 10` (למשל
  `6 + 2 + 10 = 18`) במקום `tensA*10 + tensB*10 + 10` (`60 + 20 + 10 = 90`), מה שהפיק
  שלב חשבון שקרי כמו `"60 + 20 + 10 = 18"`. `2097` מתוך `2500` שאלות שנוצרו נכשלו
  לפני התיקון; `0` אחריו.
- **תשובה יכולה הייתה לחרוג מ-`100`** — טווח העשרות בדפוס `5` (מעבר עשרה) התאים את
  עצמו לטווח הכללי (`tensA+tensB` עד `9`), אבל בשילוב עם מעבר עשרה ביחידות (עד `18`)
  זה הפיק תשובות עד `108`. תוקן ע"י הגבלת `tensCap = min(maxTens, 8)`, כך שהתשובה
  המקסימלית נשארת `98`.

תוצאת ה-property test אחרי שני התיקונים: `0` בעיות חשבון/תשובה/חריגה מ-`100` מתוך
`2500` דגימות.

**שינוי אחד מעבר לתכנון**: `tests/e2e/mika-grade2-content.spec.ts` הכיל שתי בדיקות
קיימות (מהפיצ'ר הקודם) שנכנסו ל-`חיבור עד 100` ובדקו `3` כרטיסי רמה — ציפייה שכבר
לא נכונה עכשיו שהנושא מדלג ישר לתרגול. הוחלפו ל-`חיסור עד 100` (התאום הבלתי-משתנה),
ששומר על אותה כוונת בדיקה (`3` רמות של `10`, כיווניות LTR) בלי לבדוק התנהגות שהשתנתה
בכוונה. לא נזכר במפורש ב-Affected Files כי לא היה ידוע מראש שהבדיקה הזו קיימת —
נמצא רק כש-`npm run test:e2e` הרץ הריץ אותה.

בדיקה מלאה (`npm run test:e2e`, ריצה אחת נקייה) עברה `213/213` אחרי התיקון. `npm run
build`/`npm run lint` נקיים בגרסה `1.17.0`.
