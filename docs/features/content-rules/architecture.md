# כללי תוכן שנאכפים — Architecture

## Overview
workflow אחד שמריץ בנייה, lint ובדיקות על כל PR ועל `main`; ו-`content.spec.ts`
מקבל מבנה שבו כלל חדש הוא **תוספת לרשימה** ולא בדיקה חדשה.

## Affected Files / Components
- **`.github/workflows/tests.yml`** (חדש) — מריץ `npm run build`, `npm run lint`
  ו-`npm run test:e2e`.
- **`tests/e2e/content.spec.ts`** — הכללים שחלים על כל שאלה עוברים למבנה נתונים
  אחד; הבדיקה שמריצה אותם היא אחת.
- **`.claude/skills/_shared/references/content-rules.md`** (חדש) — מתי הופכים
  הערה לכלל, ואיך.
- **`.claude/skills/_shared/references/git-workflow.md`** — הפניה לקובץ החדש.
- **`.claude/skills/qa/SKILL.md`** — הכלל נכנס לשלב שכבר קורה.
- **אין שינוי תחת `src/`**, ולכן **אין העלאת גרסה**.

## Data / State Changes
אין. שום שינוי בנתונים, בטיפוסים או ב-state של האפליקציה.

## Technical Approach

### כלל הוא שורה ברשימה, לא בדיקה חדשה

היום כל כלל ב-`content.spec.ts` הוא `test(...)` משלו עם לולאה משלו על כל השאלות.
זה עובד ל-9 כללים ולא יעבוד ל-30: כל כלל חדש מעתיק את אותה לולאה, וההודעות
נכתבות מחדש בכל פעם בפורמט מעט אחר.

**המבנה החדש:** רשימה של כללים, שכל אחד מהם `{ name, check }` — `check` מקבלת
שאלה ומחזירה הודעת בעיה או `null`. בדיקה **אחת** עוברת על כל השאלות × כל הכללים
ומדווחת את כל ההפרות יחד.

היתרונות מעשיים:
- **כלל חדש הוא רשומה אחת ברשימה.** אין לולאה להעתיק ואין בדיקה להגדיר.
- **כל ההפרות מדווחות בבת אחת** ולא רק הראשונה. מי שמוסיף כלל חדש רוצה לראות
  את כל 12 המקומות שהוא תופס, לא לתקן אחד ולהריץ שוב.
- **פורמט ההודעה אחיד** מעצם המבנה — `<id>: <מה לא בסדר>`, כפי שהעיצוב דורש,
  בלי להסתמך על מי שכותב.

כללים שאינם על שאלה בודדת — ייחודיות דימוי, מספר שאלות ברמה — נשארים בדיקות
נפרדות, כי הם על **האוסף** ולא על פריט. ניסיון לדחוף גם אותם לאותו מבנה היה
מעוות אותו.

### ה-workflow

`tests.yml`, על `pull_request` ועל `push` ל-`main`:
1. `actions/checkout`, `setup-node` עם cache.
2. `npm ci`.
3. **`npx playwright install --with-deps chromium`** — ה-runner של GitHub לא
   מגיע עם דפדפן. בלי זה כל בדיקות ה-UI ייכשלו על העדר דפדפן, וזה ייראה כמו
   כישלון של הקוד.
4. `npm run build`, `npm run lint`, `npm run test:e2e`.

**למה גם על `main`:** שני שינויים תקינים בנפרד יכולים להישבר יחד, ו-`main` נפרס
אוטומטית. תקלה כזו חייבת להתגלות מיד ולא ב-PR הבא.

**למה הכל בעבודה אחת ולא בשלוש:** `npm ci` והתקנת הדפדפן הם רוב הזמן; לפצל
היה משלש אותם כדי לחסוך שניות.

### התיעוד יושב איפה שכבר קוראים
`content-rules.md` ב-`_shared/references/` — לצד `git-workflow.md` ו-
`docs-format.md`, שכל שלב בפייפליין כבר קורא. קובץ חדש בשורש הריפו לא היה נקרא.

## Edge Cases
- **בדיקות שנכשלות ב-CI אבל עוברות מקומית** — הסיבה הצפויה היא דפדפן חסר;
  שלב ההתקנה מטפל.
- **PR שנוגע רק בתיעוד** — ה-workflow ירוץ בכל זאת. זה מקובל: דקה, והחלופה היא
  לוגיקת דילוג שתטעה יום אחד לכיוון הלא נכון.
- **כלל שנכשל על תוכן קיים ברגע שנכתב** — זו התוצאה **הרצויה**; זה בדיוק מה
  שקרה עם "אוכלים בולים". התהליך: לתקן את כל מה שנתפס באותו PR.
- **כלל שגוי שמדווח על תוכן תקין** — קרה היום פעמיים (הרמז עם `18 − 9 = 9`,
  והדימויים). **מתקנים את הכלל, לא את התוכן** — ראו `content-rules.md`.
- **ריצה במקביל ל-`version-check`** — שני workflows נפרדים, שתי בדיקות על ה-PR.
  אין ביניהם תלות.

## Risks / Tradeoffs
- **זמן CI על כל PR** — כדקה וחצי, רובה `npm ci` והתקנת דפדפן. זול לעומת תקלה
  שמגיעה לילדים.
- **המבנה החדש מחייב שכל כלל יתאים לחתימה אחת.** כלל שצריך הקשר רחב יותר לא
  ייכנס — ואז הוא נשאר בדיקה נפרדת. זה מקובל: המבנה משרת את הרוב, לא את הכל.
- **הבדיקות עדיין לא חוסמות מיזוג.** אותה מגבלה שנרשמה ב-`version-number`:
  חסימה היא הגדרת מאגר. עכשיו זה נוגע לשתי בדיקות במקום לאחת, ולכן ההוראות
  ב-`git-workflow.md` מתעדכנות לכלול את שתיהן.
