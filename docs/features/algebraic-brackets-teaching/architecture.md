# פתיחת סוגריים בביטויים אלגבריים — Architecture

## Overview
עדכון מחרוזות בלבד בתוך אובייקטי `Question` קיימים, בשני קבצי נתונים. אין שינוי
טיפוסים, רכיבים, state או ניווט — הפאנל שמרנדר `hints`/`steps` כבר קיים ומשותף
לכל שאלה באפליקציה (`QuestionExplanation` / `Practice.tsx`'s hint flow), כך
שהשינוי היחיד הוא התוכן שהוא מקבל.

## Affected Files / Components
- **`src/data/adaptiveExpressions.ts`** — פונקציית `openBrackets` (סביב שורה 67):
  להחליף את מערכי `hints` ו-`steps` בבנייה שמתאימה ל-design.md, תוך שימוש
  במשתנים הקיימים בפונקציה (`a`, `b`, `v`, `answer`) — לא להוסיף חישוב חדש, `a * v`
  התבטא כמחרוזת `${a}${v}` כמו בכל שאר הקוד (למשל `adaptivePowers.ts`).
  פונקציית `combineLikeTerms` (סביב שורה 47): להחליף רק את `hints[0]` (הוספת
  הגדרת "מקדם" למשפט הקיים) — `hints[1]`, `steps`, `prompt`, `analogy` נשארים
  בדיוק כפי שהם.
- **`src/data/grade8.ts`** — ארבעה אובייקטי `Question` קיימים ברמת `"medium"` של
  נושא "ביטויים אלגבריים": `g8-expressions-m1`, `m2`, `m6`, `m7` (סביב שורות
  89, 90, 94, 95). להחליף את שדות `hints` ו-`steps` של כל אחד למחרוזות
  הליטרליות שב-design.md (אין כאן template — אלה מספרים קבועים בקוד).

## Data / State Changes
אין. `hints` נשאר `readonly [string, string]`, `steps` נשאר מערך של
`{ label: string; math?: string }` — אותם טיפוסים, רק תוכן אחר. `prompt`,
`answer`, ו-`analogy` לא משתנים באף אחד משישה המקומות (כנדרש ב-Acceptance
Criteria).

## Technical Approach
בכל אחד מששת המקומות: להעתיק את המחרוזות בדיוק כפי שנוסחו ב-design.md, כולל
הגרשיים האחוריים סביב כל ביטוי חשבוני. בשני המחוללים (`openBrackets`,
`combineLikeTerms`) המחרוזות הן template literals שמשתמשות במשתנים הקיימים של
הפונקציה בלבד — אין להוסיף משתנה חדש או חישוב חדש; `answer` כבר מחושב
(`a * b`) ומשמש כמו שהוא. בארבעת האובייקטים ב-`grade8.ts` המחרוזות ליטרליות
לגמרי (המספרים כבר קבועים בכל שאלה), כך שאין סיכון של אי-התאמה בין הטקסט
למספרים בפועל — רק להעתיק בדיוק את הערכים שב-design.md.

## Edge Cases
- **התאמת שמות משתנים ב-`openBrackets`**: הפונקציה כבר משתמשת ב-`v` למשתנה
  (למשל `x`), לא `x` כמילולי — יש לוודא שהתבנית `${a}${v}` (לא `${a}x`) משמשת
  בכל מקום, אחרת שאלה עם משתנה `y` תציג `3x` שגוי.
- **`answer` הוא כבר `a * b`**: השלב הרביעי (`הביטוי הפתוח: ${a}${v} + ${answer}`)
  לא צריך חישוב נפרד — `answer` כבר שווה בדיוק למה שמוצג.
- **`combineLikeTerms` — לגעת רק ב-`hints[0]`**: design.md משאיר את `hints[1]`,
  `steps` ו-`analogy` בדיוק כפי שהם; פיתוי טבעי להוסיף גם שם שלב "ביטוי מכונס"
  אבל זה מחוץ להיקף שהמשתמש והמוצר הגדירו (הדפוס הזה לא כולל פתיחת סוגריים).
- **בדיקת content-rules**: יש בפרויקט כלל תוכן אוטומטי שנבדק ב-CI
  (ראו `../_shared/references/content-rules.md`) — לוודא שהמחרוזות החדשות לא
  שוברות אף כלל קיים (למשל איסור עשרוני בנתוני שאלה — לא רלוונטי כאן כי כל
  הערכים שלמים, אבל שווה לוודא ב-lint/test לפני קומיט).

## Risks / Tradeoffs
- ארבע השאלות הכתובות ב-`grade8.ts` מקבלות מחרוזות ליטרליות זהות בצורתן
  למחולל האדפטיבי, אבל בלי לחלץ helper משותף — יש כבר כפילות מכוונת בין קבצי
  התוכן הכתובים למחוללים בכל הפרויקט (זה הדפוס הקיים בכל מקום אחר), כך שזו לא
  סטייה חדשה.
- לא נגענו בשאלות הכתובות הנוספות ב-`grade8.ts` שגם שואלות "מה המקדם של" בלי
  לפתוח סוגריים (`e3`, `e5`, `e8`, `e10`, `m4`, `m9`, `h3`, `h8`) — זה נשאר לא
  עקבי איתן (הן ימשיכו בלי הגדרת "מקדם"). זו החלטת היקף מכוונת של product-spec,
  לא פספוס.
