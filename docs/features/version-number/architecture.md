# מספר גרסה במסך הראשון — Architecture

## Overview
`package.json` הוא מקור האמת היחיד למספר הגרסה. Vite מזריק אותו בזמן בנייה כקבוע
גלובלי, ומודול דק אחד חושף אותו לקוד כערך מוקלד. ההעלאה נעשית בפקודת npm אחת,
ובדיקת CI על כל PR נכשלת אם שכחו אותה.

## Affected Files / Components

**התצוגה:**
- **`package.json`** — `version` מ-`"0.0.0"` ל-`"1.0.0"`; נוספים שני scripts
  (`bump:feature`, `bump:fix`).
- **`vite.config.ts`** — קורא את `version` מ-`package.json` וחושף אותו דרך
  `define` כ-`__APP_VERSION__`.
- **`src/env.d.ts`** (חדש) — הצהרת טיפוס ל-`__APP_VERSION__`. הקובץ נכנס
  אוטומטית ל-`tsconfig.app.json` כי הוא כולל את `src`.
- **`src/data/version.ts`** (חדש) — `export const APP_VERSION` שמחזיר את הקבוע
  המוזרק. **לא מייבא כלום** (ראו Edge Cases).
- **`src/components/StudentPicker.tsx`** — שורת הגרסה בתחתית.
- **`src/App.css`** — `.app-version` ו-`.app-version-number`.

**האוטומציה:**
- **`scripts/bump-version.mjs`** (חדש) — מעלה את המספר ב-`package.json`.
- **`scripts/check-version-bump.mjs`** (חדש) — בדיקת ה-CI.
- **`.github/workflows/version-check.yml`** (חדש) — מריץ את הבדיקה על כל PR.
- **`.claude/skills/_shared/references/git-workflow.md`** — הכלל מתועד שם, כי
  הוא חל גם על תיקונים שלא עוברים ב-`/feature`.
- **`.claude/skills/developer/SKILL.md`** — שלב ההעלאה נוסף לרצף שה-developer
  כבר מבצע ממילא.

## Data / State Changes
אין state, אין props חדשים, אין שינוי במבנה נתונים. `APP_VERSION` הוא קבוע
מחרוזת שנקבע בזמן הבנייה ולא משתנה בזמן ריצה. אין שמירה ב-localStorage.

## Technical Approach

### מקור האמת: למה `package.json` ולא קובץ TS

שלוש אפשרויות נשקלו. הבחירה היא **`package.json` בלבד**, מהסיבות הבאות:

- זה המקום המוסכם. מי שנכנס לריפו מחפש שם גרסה, ולא בקובץ `src/data/`.
- הוא כבר קיים ומכיל `version` — קובץ TS נפרד היה יוצר **מקור אמת שני**, בדיוק
  מה שה-product-spec אוסר במפורש.
- הוא ניתן לעריכה בכלים סטנדרטיים, כך שסקריפט ההעלאה הוא חמש שורות בלי תלויות.

**איך הערך מגיע לקוד:** `vite.config.ts` קורא את `package.json` ומעביר את
המחרוזת ל-`define: { __APP_VERSION__: JSON.stringify(version) }`. Vite מבצע
החלפה טקסטואלית בזמן הבנייה — אין קריאת קובץ בזמן ריצה, אין fetch, וזה עובד
באתר סטטי לגמרי. אותו מנגנון פועל גם ב-`npm run dev`, ולכן גם בבדיקות
Playwright, שמריצות את שרת הפיתוח.

**למה בכל זאת יש `src/data/version.ts`:** כדי שקומפוננטות ייבאו מודול רגיל
ומוקלד ולא יגעו בקבוע גלובלי-קסום. הקובץ **לא מכיל את המספר** אלא רק מייצא
אותו, כך שמקור האמת נשאר יחיד. זה גם מרכז את הנקודה היחידה שבה הגלובל נוגע
בקוד — אם המנגנון יוחלף בעתיד, יש קובץ אחד לשנות.

**למה לא לייבא את `package.json` ישירות ל-React:** זה היה מכניס את כל הקובץ,
כולל רשימת ה-devDependencies, לתוך ה-bundle שנשלח לדפדפן. רעש מיותר בהורדה
עבור מחרוזת אחת.

### התצוגה

`StudentPicker` מרנדר בתחתית, אחרי `.student-list`, אלמנט עם שני ילדים נפרדים:
התווית `גרסה` ואלמנט נפרד למספר. **שני אלמנטים, לא מחרוזת אחת** — זו דרישה
מפורשת מ-design.md ומכלל הפרויקט ב-`CLAUDE.md`.

ב-CSS: `.app-version` מקבל את הגודל והצבע המעומעם, ו-`.app-version-number` מקבל
`direction: ltr` **וגם** `unicode-bidi: isolate`. התקדים בקובץ הוא `.step-math`
(שורות 211-212 ב-`App.css`) — אותה תבנית בדיוק.

### האוטומציה: שלוש שכבות, ורק השלישית באמת מחייבת

זו הנקודה שהוגדרה כחשובה, ולכן היא נכתבת בכנות: **הוראה בקובץ markdown היא לא
אוטומציה.** הפרויקט הזה כבר הוכיח את זה — דפי הסטטוס התיישנו כי העדכון שלהם היה
הוראה שצריך לזכור, והם תוקנו רק היום ב-PR #9. אותו מנגנון בדיוק יתן אותה תוצאה
בדיוק. לכן:

**שכבה 1 — לעשות את זה זול.** שתי פקודות:
```
npm run bump:feature   # middle+1, minor→0
npm run bump:fix       # minor+1
```
`scripts/bump-version.mjs` קורא את `package.json`, מפרק את `major.middle.minor`,
מעלה לפי הארגומנט וכותב בחזרה. בלי תלויות חיצוניות, בלי git tag, בלי commit —
רק עריכת הקובץ, כך שהשינוי נכנס לקומיט של השלב שממילא נעשה. `major` אינו נתמך
כארגומנט **בכוונה**: הוא נערך ידנית, וסקריפט שיודע להעלות אותו הוא סקריפט
שמישהו יריץ בטעות.

**שכבה 2 — לתעד איפה שמסתכלים.** הכלל נכנס ל-`git-workflow.md` (כי תיקונים לא
עוברים ב-`/feature` ולכן לא יראו את קובץ ה-skill שלו) ולשלב ה-developer, שכבר
מריץ build ו-lint ממילא. זה מגדיל את הסיכוי שזה יקרה, אבל **לא מבטיח כלום**.

**שכבה 3 — לאכוף.** `.github/workflows/version-check.yml` רץ על כל pull request:
1. מושך את הענף ואת ה-base במלואם.
2. **מדלג** אם ה-PR לא נוגע ב-`src/`, ב-`index.html` או ב-`public/` — ראו
   ההחלטה למטה.
3. משווה את `version` ב-HEAD מול הערך ב-base.
4. לפי הקידומת של שם הענף: `feature/*` דורש ש-`middle` עלה ב-1 ו-`minor` אופס;
   `fix/*` דורש ש-`minor` עלה ב-1. קידומת אחרת — הבדיקה מדלגת עם הודעה.
5. שינוי ב-`major` מתקבל תמיד ומדווח כהודעה, לא ככשל — הוא ידני ומכוון.

**ההחלטה שנגזרת מכאן:** PR שנוגע רק בתיעוד (כמו PR #9) **אינו** מחייב העלאת
גרסה. מספר הגרסה מתאר את מה שהמשתמש רואה באפליקציה; להעלות אותו בגלל תיקון
במסמך היה הופך אותו למספר שמשקר. זו הסיבה לשלב הדילוג בסעיף 2.

## Edge Cases

- **תלות מעגלית** — הכשל שהפיל את האפליקציה למסך לבן בעבר (`grade1.ts` ↔
  `curriculum.ts`, ראו `CLAUDE.md` ו-`src/data/level.ts`). `version.ts` **אינו
  מייבא דבר** ולכן אינו יכול להשתתף במעגל. זה לא במקרה — כל קובץ נתונים חדש
  בפרויקט הזה צריך להיות עלה בגרף התלויות אלא אם יש סיבה חזקה אחרת.
- **`__APP_VERSION__` לא מוגדר** — קורה אם מריצים קוד מחוץ ל-Vite. לא רלוונטי
  כאן: אין vitest בפרויקט, ובדיקות ה-e2e רצות מול שרת הפיתוח של Vite. אם בעתיד
  יתווסף runner שלא עובר דרך Vite, `version.ts` הוא המקום היחיד שיצטרך fallback.
- **כיווניות** — `direction: ltr` **וגם** `unicode-bidi: isolate`. ראו
  design.md: זה כנראה מיותר טכנית עבור `1.0.0`, ומיושם בכל זאת.
- **גרסה עם מספר דו-ספרתי** (`1.12.3`) — עובד; הסקריפט עובד על מספרים שלמים ולא
  על ספרה בודדת, והתצוגה היא מחרוזת.
- **ה-CI רץ על PR מ-fork** — `github.head_ref` ריק במקרים מסוימים; הבדיקה
  מדלגת במקום להיכשל. אין fork בפרויקט הזה, אבל כשל שקרי חוסם מיזוג.
- **שני PR-ים פתוחים במקביל** — שניהם יעלו מ-`1.0.0` ל-`1.1.0`, והשני יקבל
  התנגשות מיזוג ב-`package.json`. זה **רצוי**: ההתנגשות מכריחה החלטה מודעת
  איזה מספר נכון, במקום ששני פיצ'רים ישבו בשקט על אותה גרסה.

## Risks / Tradeoffs

- **בדיקת ה-CI מוודאת ש*משהו* עלה, לא שעלה *הנכון*.** היא נשענת על קידומת שם
  הענף כדי לדעת מה לצפות. תיקון שנדחף בענף `feature/` יעבור את הבדיקה ויעלה
  `middle`. זה מקובל: מוסכמת שמות הענפים כבר מחייבת בפרויקט מאז PR #1, ובדיקה
  שתופסת 90% מהשכחות עדיפה על אפס.
- **סיווג "פיצ'ר מול תיקון" נשאר שיפוט אנושי.** אין ואי אפשר שתהיה אוטומציה
  לזה. כל מה שהמנגנון הזה מבטיח הוא שההחלטה תתקבל במפורש ולא תישכח.
- **המספר לא מתאר את ההיסטוריה שקדמה לו.** ששת הפיצ'רים שכבר מוזגו לא נספרים —
  החלטה מפורשת של ה-product-spec.
- **תוספת קובץ workflow שני לריפו.** נשקל לוותר על שכבה 3 ולהסתפק בהוראות, אבל
  זה בדיוק המנגנון שכבר נכשל כאן פעם אחת היום. עלות: קובץ אחד וכ-40 שורות.
- **`define` הוא החלפה טקסטואלית.** אם מישהו יכתוב `__APP_VERSION__` בתוך
  מחרוזת בקוד, היא תוחלף גם שם. הסיכון תיאורטי בשם כה ייחודי.
